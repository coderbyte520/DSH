# Agent Note: 在本地裸 PTY 中应答光标位置查询

Status: implemented

[English](2026-10-13-bare-pty-cursor-query.md) | 中文

## 问题

在当前这台 Ubuntu 运行器镜像上，所有持久 pwsh 套件都会失败：`terminal-bash` 的真实 shell 用例返回空 viewport 或提交行的字面回显，`tool-pwsh-persistent` 的 loader-composition 用例则报出产品自身的 20 秒命令超时。提交的命令从未执行。

pwsh 7.6.6 搭配 PSReadLine 2.4.5 会在读取任何输入之前先向终端提问：`ESC[6n`，即设备状态报告 6——"光标在哪里？"。裸伪终端之上没有任何模拟器可以应答，于是子进程无限等待，永远到不了自己的输入循环，消费方的写入滞留在输入队列里——行规程把它们回显出来，却没有任何东西执行它们。在 harness 之外复现该会话显示：全部输出只有四个字节（`ESC[6n`）；任何有效应答都能让两次提交执行；而创建时没有窗口尺寸的 PTY 会让 PSReadLine 的渲染器除零（`BufferWidth: 0`）。第二个故障已被解析出的 `rows`/`cols` 防住。只回答原位仍然不够：子进程其后每次重绘都会定位到第 1 行，落在保留文本里就是重绘历史——完成标记确实出现了，但后端的读取与提示符尾部就绪判定看到的是一行被逐字符重绘的内容。

在 POSIX 上 `node-pty` 分配的是裸内核 PTY，因此 harness 之下没有任何一层能够应答；本地提供方持有唯一能看到双向数据的连接。在 Windows 上 `node-pty` 分配 ConPTY，它本身就是终端模拟器，会自行应答。

## 决策

- `LocalTerminalHandle` 扫描每个解码后的输出分块以查找 `ESC[6n`，并在除 `win32`（ConPTY 自身即模拟器）之外的每个平台上应答。扫描器保留上一分块的最后两个字符，因此跨两个分块到达的查询同样能匹配。
- 应答报告 `TerminalCursor` 从子进程自身输出跟踪出的位置——可打印字符、回车、换行、退格与绝对光标定位，并在 PTY 解析出的行列范围内换行与滚动。固定原位不够：子进程其后每次重绘都会定位到第 1 行，落在保留文本里就是错误的那一行。
- `TerminalSanitizer` 增加了配套的行模型：分块会报告 `retract`，即其文本替换掉自身当前行的多少个字符；会话在追加之前从 scrollback 与活跃 send 的 viewport 中删除相应数量。可打印字符、CR、LF 与退格推进该模型，绝对光标定位移动写入列，`ESC[K` 擦除到行尾。
- 清洗器同时持有自有标记之后的**渲染尾部**，会话以它替换自己保存的尾部，而不是逐块累积。因此重写提示符的重绘会再次报告该提示符，而不是追加第二份副本——这正是行编辑期间提示符就绪判定能够持续成立的原因。
- 传输层会应答每个分块携带的**每一条**光标查询，而不只是第一条：未应答的查询会让子进程等到自身超时，在就绪判定看来就是一段静默。
- pwsh 启动只有在保留文本**以受控提示符结尾**时才发布会话。引导行安装的 prompt 函数源码里含有提示符字符串，而行编辑器会回显该源码，所以此前"文本内任意位置匹配"的判定会发布一个尚未到达提示符的 shell——测试的下一次 send 打在这个仍在忙的 shell 上，最终结算为推断空闲。
- 两个提供方的 README 都记录了该行为：subprocess README 记录跟踪应答与模型只覆盖按行移动的限制，terminal README 记录保留行的契约。

## 曾考虑的替代方案

**改在 `terminal-bash` 后端应答。** 已否决：后端收到的是解码后的文本，负责提示符就绪、缓冲区策略与面向模型的操作；而该查询是任何 PTY 子进程都可能提出的终端协议问题，并且只有传输层知道另一端是否已经存在模拟器（Windows 上的 ConPTY 就是）。

**让 PowerShell 不再提问。** 从 pwsh 引导处移除 PSReadLine 或以 `-NonInteractive` 启动都无法奏效：子进程在读取任何输入之前就已阻塞，任何引导命令都不会被执行。该查询也并非 PowerShell 独有。

**只在 pwsh 方言下应答。** 已否决：该方言的后端需要的正是它刻意看不到的原始字节，而且 bash 子进程同样可能提出这个问题。

**固定回答原位。** 经实测否决：它能解除阻塞，但此后每次重绘都被定位到第 1 行，保留文本变成重绘历史，后端的提示符尾部就绪判定也退化为推断空闲。跟踪位置才能让子进程的模型与它正在写入的 PTY 保持一致。

**缓冲整行后再重新输出。** 已否决：消费方是流式的，就绪判定会在文本到达时读取标记之后的内容，若把一行留到终止符再输出，就会推迟就绪判定所匹配的提示符文本。让分块报告它替换了当前行的多少内容，可以保持这一流式契约不变。

**引入终端模拟器依赖。** 目前否决：保留文本的契约需要按行渲染而不是屏幕，上述两个模型已覆盖本仓库 shell 会发出的内容。若将来某个消费方真的需要渲染屏幕，再重新评估。

## 后果

- 在 POSIX 上查询光标位置的子进程现在能继续运行，这正是持久 pwsh 会话在 Linux 上可用的前提。
- 光标模型只覆盖按行的移动：滚动区域、制表符与相对光标移动不在此列，因此驱动全屏布局的子进程可能出现位置漂移。消费方保留的是文本而不是屏幕。
- 撤回是按行的：一次重绘可以替换当前行的保留尾部，但绝不会触及更早的行，因为清洗器在每个 CR 与 LF 处重置列。
- 应答只送往子进程，因此绝不会出现在面向模型的输出流中。
- Windows 不受影响；ConPTY 自行应答同一查询，重复应答会把该报告注入子进程的输入。
- 单元测试覆盖扫描器与光标模型（有查询、跨分块、无查询、退出之后、Windows 直通、换行、光标定位与行重置）以及清洗器的撤回（整行重绘、局部重写、擦除到行尾、跳格填充）。行为本身仍以 Linux 套件为验收路径；只要有 POSIX PTY 车道启动就会执行它们。
