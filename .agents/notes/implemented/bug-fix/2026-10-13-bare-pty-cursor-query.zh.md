# Agent Note: 在本地裸 PTY 中应答光标位置查询

Status: implemented

[English](2026-10-13-bare-pty-cursor-query.md) | 中文

## 问题

在当前这台 Ubuntu 运行器镜像上，所有持久 pwsh 套件都会失败：`terminal-bash` 的真实 shell 用例返回空 viewport 或提交行的字面回显，`tool-pwsh-persistent` 的 loader-composition 用例则报出产品自身的 20 秒命令超时。提交的命令从未执行。

pwsh 7.6.6 搭配 PSReadLine 2.4.5 会在读取任何输入之前先向终端提问：`ESC[6n`，即设备状态报告 6——"光标在哪里？"。裸伪终端之上没有任何模拟器可以应答，于是子进程无限等待，永远到不了自己的输入循环，消费方的写入滞留在输入队列里——行规程把它们回显出来，却没有任何东西执行它们。在 harness 之外复现该会话显示：全部输出只有四个字节（`ESC[6n`）；补上 `ESC[1;1R` 后两次提交都能执行；而创建时没有窗口尺寸的 PTY 会让 PSReadLine 的渲染器除零（`BufferWidth: 0`）。第二个故障已被解析出的 `rows`/`cols` 防住。

在 POSIX 上 `node-pty` 分配的是裸内核 PTY，因此 harness 之下没有任何一层能够应答；本地提供方持有唯一能看到双向数据的连接。在 Windows 上 `node-pty` 分配 ConPTY，它本身就是终端模拟器，会自行应答。

## 决策

- `LocalTerminalHandle` 扫描每个解码后的输出分块以查找 `ESC[6n`，并在除 `win32` 之外的每个平台上向子进程写回 `ESC[1;1R`。扫描器保留上一分块的最后两个字符，因此跨两个分块到达的查询同样能匹配。
- 应答始终报告原位。传输层不持有光标模型，其消费方保留的是文本而不是屏幕。
- 提供方 README 在终端进程条目中记录该行为，并在"已知限制"中记录固定的原位应答。

## 曾考虑的替代方案

**改在 `terminal-bash` 后端应答。** 已否决：后端收到的是解码后的文本，负责提示符就绪、缓冲区策略与面向模型的操作；而该查询是任何 PTY 子进程都可能提出的终端协议问题，并且只有传输层知道另一端是否已经存在模拟器（Windows 上的 ConPTY 就是）。

**让 PowerShell 不再提问。** 从 pwsh 引导处移除 PSReadLine 或以 `-NonInteractive` 启动都无法奏效：子进程在读取任何输入之前就已阻塞，任何引导命令都不会被执行。该查询也并非 PowerShell 独有。

**只在 pwsh 方言下应答。** 已否决：该方言的后端需要的正是它刻意看不到的原始字节，而且 bash 子进程同样可能提出这个问题。

**维护光标模型以给出真实应答。** 已否决：真实应答意味着一台终端模拟器——需要解析光标移动、擦除与滚动——而本 harness 刻意不具备这些，其消费方又会剥掉转义并保留文本，因此报告的位置毫无收益。为应答一次查询而引入模拟器依赖并不相称；若将来某个消费方真的需要渲染屏幕，这个判断需要重新评估。

## 后果

- 在 POSIX 上查询光标位置的子进程现在能继续运行，这正是持久 pwsh 会话在 Linux 上可用的前提。
- 应答是固定的原位：依据该应答自行定位输出的子进程会按第 1 行第 1 列渲染。本仓库运行的 shell 都通过自身 prompt 函数重绘，且消费方的输出是文本。
- 应答只送往子进程，因此绝不会出现在面向模型的输出流中。
- Windows 不受影响；ConPTY 自行应答同一查询，重复应答会把该报告注入子进程的输入。
- 单元测试覆盖扫描器（有查询、跨分块、无查询、退出之后、以及 Windows 直通）。行为本身仍以 Linux 套件为验收路径；只要有 POSIX PTY 车道启动就会执行它们。
